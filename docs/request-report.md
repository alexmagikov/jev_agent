# Запросы пайплайна: структура данных, объём и бюджет

Срез локального кода на 16 октября 2026 года. Режим: `full`, настройки из
`notebooks/colab_ollama.ipynb`: Ollama, `qwen2.5:7b`, `json_schema`,
`temperature=0`, максимум две попытки извлечения.

Числа и таблицы в тексте ниже описывают **исторический срез от 16 октября**, а не
текущий бюджет. JSON-примеры по ссылкам обновлены генератором 18 октября после
изменения правил и вопросов; актуальные размеры находятся в
[request-examples/sizes.json](request-examples/sizes.json). У заполненной суммы
счёта появилась отдельная проверка неоднозначности, у атрибутов позиций — точечные
вопросы; историческая формула числа вопросов ниже их не учитывает.

Размеры исторического среза получены локально через
сборщики приложения и установленного `typesafe-sdk==0.7.2`, без вызовов API.
Учебное предложение для C001 составлено вручную и прошло локальную проверку.
Оно иллюстрирует успешную ветку, но не является результатом нового прогона модели.

Для C001 успешная ветка состоит из трёх запросов: классификация Jev — **5 155 байт**,
извлечение LLM — **23 960 байт**, проверка Jev — **42 211 байт**. Исходная реплика
занимает 90 символов; основной объём создают инструкции, схемы и проверочные вопросы.
Известные **6 044 токена** относятся к двум попыткам LLM в более раннем запуске.
Оценка **4 млн токенов** — сценарный запас на эксперименты, не измеренный расход.

## 1. Что именно вызывается

В пайплайне три вида запросов. В обычном успешном кейсе со счётом или переводом
выполняется по одному запросу каждого вида.

| Этап                      | Получатель                        | Передаваемые данные                                                                                                                                          | Ответ                                                                                                                   |
| ----------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Классификация    | Jev, `POST /v1/systemone`                 | Диалог и два вопроса типа `choice` с правилами и критериями                                                                        | Тип документа, уверенность, вероятности вариантов; причина для `none` |
| Извлечение          | Ollama / LLM, `POST /v1/chat/completions` | Системные инструкции, диалог, выбранный тип, шаблон полей, JSON Schema, замечания предыдущей попытки | JSON: значения, статусы, цитаты, формулы                                                         |
| Проверка смысла | Jev, `POST /v1/systemone`                 | Диалог, шаблон, предложение LLM, проверенные Python поля и пакет вопросов `noul`                                         | Оценка вероятности указанной ошибки для каждого вопроса                     |

В Colab LLM находится по адресу `http://127.0.0.1:11434` в той же среде исполнения.
Jev вызывается отдельно через TypeSafe SDK. В установленном SDK адрес по умолчанию
`https://api.typesafe.ai`, модель по умолчанию `jev-latest`; SDK допускает их
переопределение через `TYPESAFE_BASE_URL` и `TYPESAFE_DEFAULT_MODEL`.
Отчёт использует именно значения по умолчанию и не читает окружение Colab.

`response_model` у Jev — локальный Pydantic-класс для разбора ответа.
**Его JSON Schema не передаётся серверу.** Это проверено по сборщику запросов
установленного SDK. Тело Jev содержит `state`, `model`, `questions`.

`labels.jsonl` используется для локальной оценки качества и отладочного вывода.
Эталоны, README и исходный код в запросы к моделям не входят. `case_id` и `split`
остаются на стороне приложения; внутри диалога передаются ID реплик.

## 3. Вход и классификация Jev

Один кейс — один диалог. Учебный пример C001:

```json
{
  "case_id": "C001",
  "split": "dev",
  "messages": [
    {
      "id": "m1",
      "role": "user",
      "text": "Выставь счет ООО Ромашка, ИНН 7701234567, за консультационные услуги 5000 рублей, без НДС."
    }
  ]
}
```

Структура запроса классификации, с сокращёнными инструкциями:

```json
{
  "state": {"messages": [{"id": "m1", "role": "user", "text": "..."}]},
  "model": "jev-latest",
  "questions": {
    "document_type": {
      "type": "choice",
      "instructions": {"question": "...", "state_scope": "...", "evidence_rule": "..."},
      "criteria": {"invoice_draft": "...", "transfer_draft": "...", "none": "..."}
    },
    "none_reason": {
      "type": "choice",
      "instructions": "...",
      "criteria": {"no_request": "...", "other_document": "...", "cancelled": "..."}
    }
  }
}
```

Оба вопроса отправляются **одним HTTP-запросом**. Второй ответ используется только
при `document_type=none`; иначе игнорируется. Ответ `choice` содержит выбранный
вариант, уверенность и распределение вероятностей. Приложение сохраняет выбранный
тип и уверенность; текст причины `none` подставляется из локального словаря.

Полное тело: [01-jev-classification.request.json](request-examples/01-jev-classification.request.json).

## 4. Запрос к LLM

LLM получает два сообщения верхнего уровня:

```text
messages[0]: role=system, content=EXTRACTION_PROMPT
messages[1]: role=user,   content=JSON-строка с контекстом задачи
```

Второе `content` после декодирования JSON имеет следующую структуру:

| Ключ          | Содержимое                                                                       | Назначение                                                    |
| ----------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| `document_type` | `invoice_draft` или `transfer_draft`                                                | Уже выбранный тип; модель его не меняет |
| `template`      | Описание документа и словарь имён/описаний полей | Смысл каждого поля                                      |
| `messages`      | Весь диалог: `id`, `role`, `text`                                          | Источники значений и контекст                 |
| `output_schema` | JSON Schema конкретного типа документа                             | Структура допустимого ответа                  |
| `feedback`      | Массив строк; `[]` на первой попытке                           | Ошибки предыдущей попытки                        |

Внешнее тело запроса, с сокращённым содержимым:

```json
{
  "model": "qwen2.5:7b",
  "messages": [
    {"role": "system", "content": "<правила извлечения>"},
    {"role": "user", "content": "<JSON-строка: document_type, template, messages, output_schema, feedback>"}
  ],
  "max_tokens": 4096,
  "temperature": 0.0,
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "invoice_draft_extraction",
      "strict": true,
      "schema": {"...": "полная JSON Schema"}
    }
  }
}
```

Полное тело: [02-llm-extraction.request.json](request-examples/02-llm-extraction.request.json).
JSON Schema фактически присутствует дважды: внутри пользовательского `content`
и в `response_format.json_schema.schema`. Это увеличивает HTTP-тело. Нельзя
автоматически считать обе копии одинаковым числом входных токенов: обработка
служебного `response_format` зависит от сервера.

`4096` — верхний предел выходных токенов, а не обязательный расход на ответ.
В обычных настройках приложения без явного `LLM_RESPONSE_FORMAT` используется
`json_object`; измерения отчёта относятся к `json_schema` из notebook.

## 5. Структура ответа LLM и результата Python

Ответ LLM — объект `{"fields": {...}}`. У счёта 12 обязательных полей,
у перевода 5. Неизвестные поля всё равно включаются со статусом `missing`.

| Тип             | Ключи `fields`                                                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `invoice_draft`  | `recipient_name`, `recipient_inn`, `recipient_email`, `recipient_account`, `recipient_bik`, `subject`, `items`, `amount_rub`, `vat_mode`, `vat_rate_percent`, `basis_number`, `basis_date` |
| `transfer_draft` | `amount_rub`, `destination_card_masked`, `destination_bank`, `source_account_kind`, `recipient_relation`                                                                                                 |

У каждого поля одинаковая оболочка:

```json
{
  "status": "fillable",
  "value": 5000,
  "evidence": [{"message_id": "m1", "quote": "5000 рублей"}],
  "calculation": null
}
```

`status` допускает `fillable`, `missing`, `ambiguous`, `invalid`.
Тип `value` определяется конкретным полем: строка, число или список позиций.
При отсутствии значения возвращается `null`.

`items` — тоже объект поля, а список находится в `items.value`. Одна позиция:

```json
{
  "description": "консультационные услуги",
  "quantity": null,
  "unit": null,
  "unit_price_rub": null,
  "quantity_calculation": null,
  "unit_price_calculation": null
}
```

Формула находится рядом с вычисляемым значением. Структура:
`{"expression":"total / count","operands":[{"name":"total","source":{"message_id":"m1","quote":"100"}}, ...]}`.
Это пример формы, не формула для C001. Для вычисляемого значения LLM оставляет
`null`; Python подставляет исходные числа и выполняет разрешённые операции.
В актуальном коде формулы допускаются у `amount_rub` и числовых частей позиций.
Ставка `vat_rate_percent` заполняется только явно указанным процентом, без формулы.
Сохранённые JSON-примеры запросов и размеры ниже относятся к срезу от 16 октября;
для обновления снимка используйте скрипт экспорта из раздела 12.

Python проверяет схему, точное присутствие цитат, роли и ID источников,
числовые основания, форматы и арифметику. Детерминированные проверки не вызывают API.
После обработки поле содержит `status`, `value`, `evidence` из ID реплик и
`derivation` — описание расчёта либо `null`. Объекты формул в итог не сохраняются.

Примеры целиком:
[предложение LLM](request-examples/03-llm-response.example.json),
[поля после Python](request-examples/04-python-fields.example.json).
Оба примера учебные; измеренный размер ответа не означает измеренного расхода выходных токенов.

## 6. Проверка Jev: сколько вопросов и что в state

В одном запросе передаётся:

```text
state
├── messages          весь исходный диалог
├── document_type     выбранный тип
├── template          описание и поля документа
├── proposal          предложение LLM, включая цитаты и формулы
└── checked_fields    значения после проверок и вычислений Python

questions
├── recipient_name::unsupported  {type: "noul", instructions: "..."}
├── recipient_name::wrong_role   {type: "noul", instructions: "..."}
├── recipient_name::superseded   {type: "noul", instructions: "..."}
└── ... остальные проверки
```

Для каждого `fillable` поля создаются три вопроса: подтверждено ли значение,
не перепутана ли его принадлежность, не отменено ли оно поздним исправлением.
Для остальных статусов — один вопрос о правильности статуса. Для заполненного
`items` добавляется проверка пропущенных позиций/атрибутов; для поля с расчётом —
проверка смысла формулы.

Число вопросов: **Q = N + 2F + I + D**, где N — число полей, F — число
`fillable` полей, I = 1 при заполненном `items`, D — число полей с `derivation`.
В учебном C001: 12 полей, 6 заполненных, `items` заполнен, формул нет:
**12 + 2 × 6 + 1 = 25 вопросов в одном запросе**.

У каждого вопроса `instructions` включают общие `_RULES`, а у вопросов к
`items` и `subject` — ещё `_ITEMS_RULES`. В C001:

| Повторяющаяся часть                        | Символов в одной копии | Копий | Символов всего |
| ------------------------------------------------------------ | ----------------------------------------: | ---------: | --------------------------: |
| Общие правила                                    |                                       976 |         25 |                      24 400 |
| Правила позиций и предмета счёта |                                       991 |          7 |                       6 937 |
| Итого                                                   |                                        — |         — |                      31 337 |

Таким образом, примерно 77% символов полного тела проверки занимают эти
повторяющиеся правила. Это измерение сериализованного запроса; внутренние
вычисления, токенизация и тарификация Jev из него не следуют.

Полное тело: [05-jev-verification.request.json](request-examples/05-jev-verification.request.json).
Полезная часть ответа, с условным значением:

```json
{"answers": {"items::unsupported": {"noul": 0.89}}}
```

В настоящем ответе должны быть все запрошенные ключи. Код трактует `noul` как
оценку вероятности **указанной ошибки**. Значения от `0.7` включительно формируют
замечания; если замечаний нет, результат принимается. Это семантическая проверка
по диалогу, а не сравнение с `labels.jsonl` и не гарантия правильности.

## 7. Что повторно отправляется

При ошибке повторяется полный запрос извлечения: системные инструкции, весь
исходный диалог, выбранный тип, шаблон и схема. Меняется `feedback`.
Предыдущий JSON-ответ модели в запрос не включается. История замечаний всех
попыток не накапливается: передаются замечания последней попытки.
Зафиксированных правильных полей и частичного исправления сейчас нет —
модель заново возвращает весь набор полей.

В текущем коде замечание Jev содержит только имя проверки, вероятность ошибки и
конкретный вопрос. Общие `_RULES` и `_ITEMS_RULES` в `feedback` не передаются.
Таблица и JSON-примеры ниже сохраняют прежний срез с полными инструкциями;
их размеры не описывают текущий сокращённый `feedback`.

| Источник замечания | Содержимое `feedback`                                                                                     | Дополнительный объём HTTP-тела в примере |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------: |
| Python                              | Одна строка «Цитата источника отсутствует в указанной реплике» |                                                             95 байт |
| Jev                                 | Имя проверки, оценка и **полный текст её инструкций**                  |                            2 236 байт для `items::unsupported` |

Примеры повторов: [после Python](request-examples/06-llm-retry-python.request.json),
[после Jev](request-examples/07-llm-retry-jev.request.json).
Замечания в них смоделированы для демонстрации формата, это не запись реального
отклонения учебного корректного ответа. Полные тела имеют 24 055 и 26 196 байт.

Повтор из-за HTTP-ошибки/timeout — другой механизм: повторяется тот же payload
без новых замечаний. В notebook разрешён один сетевой повтор на вызов извлечения.
У TypeSafe SDK есть собственные сетевые повторы, отдельно от этого лимита.

Без сетевых повторов число API-вызовов на кейс:

| Сценарий                                                                   | Классификация Jev | Извлечение LLM | Проверка Jev | Всего |
| ---------------------------------------------------------------------------------- | -----------------------------: | -----------------------: | -------------------: | ---------: |
| Тип `none`                                                                    |                              1 |                        0 |                    0 |          1 |
| Принят с первой попытки                                        |                              1 |                        1 |                    1 |          3 |
| Первая попытка отклонена Python, вторая принята |                              1 |                        2 |                    1 |          4 |
| Первая отклонена Jev, вторая дошла до Jev              |                              1 |                        2 |                    2 |          5 |
| Обе попытки отклонены Python                                    |                              1 |                        2 |                    0 |          3 |

передаются и при извлечении перевода.

## 9. Что известно о токенах

Есть предоставленный пользователем лог более раннего прогона C001:

```text
LLM: запросов=2, сетевых повторов=0
вход=4603, выход=1441; usage получен для 2/2 ответов
```

Это **6 044 токена суммарно за две попытки одного кейса**:
4 603 входных и 1 441 выходной. Обе попытки тогда были отклонены до семантической
проверки Jev. Число не описывает расход всех трёх этапов и не является средним
по датасету. После того прогона промпт и схема менялись.

Для текущих запросов точного числа токенов в этом отчёте нет: измерение офлайн
не запускало модель и не использовало её токенизатор. Символы и байты нельзя
выдавать за точные токены. Ранее названные 1 800–2 400 токенов системного промпта
были приблизительной оценкой, а не измерением.

Сейчас `LLMUsage` суммирует `usage.prompt_tokens` и `usage.completion_tokens`
ответов LLM по всему прогону, включая ответы, отклонённые проверками.
Расход Jev в эту сумму не входит:

- ответ классификации содержит `usage`, но `classify_document` его не переносит
  в итоговый `DocumentTypeDecision` и не агрегирует;
- `VerificationResponse` сохраняет только `answers`, поэтому usage проверки
  не используется;
- при сетевом сбое без полученного usage фактический серверный расход неизвестен.

Следовательно, текущий лог позволяет оценить только **сообщённый API расход
извлечения**, а не полную стоимость пайплайна.

## 10. Как обосновать бюджет вместо «нужно 4 млн»

Разметка текущего набора:

| Выборка | Счёт | Перевод | `none` | Всего | Нуждается в LLM при верной классификации |
| -------------- | -------: | -------------: | -------: | ---------: | -----------------------------------------------------------------------: |
| dev            |       19 |              4 |        5 |         28 |                                                                       23 |
| test           |        8 |              3 |        2 |         13 |                                                                       11 |
| Всего     |       27 |              7 |        7 |         41 |                                                                       34 |

Точная формула для измеренного прогона:

```text
T_LLM = сумма по всем полученным ответам (input_tokens + output_tokens)
```

Для планирования будущих экспериментов:

```text
T_LLM ≈ число прогонов × число кейсов с извлечением
        × средний расход на один такой кейс с учётом исправлений
```

Модели сравнения и точечные повторные эксперименты добавляются отдельными
слагаемыми. Расход классификации и верификации Jev нужно учитывать отдельно.
Сетевые повторы требуют дополнительного резерва; не всякий сбой даёт usage.

**Только иллюстрация масштаба на старом замере**, не прогноз текущего промпта:

| Эксперимент на dev                                                                                                           | Условный расход LLM |
| ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------: |
| 1 прогон, условно 3 022 токена/кейс — половина старого двухпопыткового замера |                            69 506 |
| 1 прогон, условно 6 044 токена/кейс                                                                                |                           139 012 |
| 3 таких прогона                                                                                                               |                           417 036 |
| 10 таких прогонов                                                                                                            |                         1 390 120 |
| 20 таких прогонов                                                                                                            |                         2 780 240 |

При этом допущении 4 млн — примерно **29 полных dev-прогонов** с расходом
6 044 токена на каждый из 23 кейсов извлечения. Это запас на большое число
экспериментов, а не измеренная потребность разработки. Предыдущая оценка,
умножавшая расход извлечения на все кейсы, также не учитывала пропуск `none`.

Для сравнения платной модели с локальной разумно сначала измерить небольшой
фиксированный dev-набор на текущем промпте, затем посчитать бюджет нужного числа
прогонов. Test следует оставить для финальной оценки. Число повторов, качество
и токенизация другой модели заранее неизвестны.

## 11. Что измерять и сокращать дальше

Это предложения следующих шагов; поведение пайплайна при подготовке отчёта не менялось.

1. Сохранять расход отдельно по `case_id`, этапу, модели и номеру попытки:
   входные/выходные токены, размер тела, время, результат проверки и причину повтора.
   Для Jev сохранять доступный usage обоих этапов. Отсутствие usage обозначать как
   неизвестное значение, а не ноль.
2. Проверить возможность сокращения повторяющихся правил Jev. Вынесение общих
   правил требует проверки поведения API и качества: данные в `state` не становятся
   инструкциями автоматически. Уменьшение байтов не гарантирует равной экономии токенов.
3. Проверить необходимость полной копии JSON Schema внутри `user.content`, когда
   она уже задана в `response_format`. Сравнить реальный usage и качество до/после.
4. Разделить инструкции счёта и перевода; передавать только правила выбранного типа.
5. Сокращение feedback уже реализовано: передаются имя проверки, вероятность и
   конкретный вопрос без общих инструкций Jev. Частичное исправление полей — отдельное изменение архитектуры:
   сейчас оно не реализовано и требует учёта зависимостей между полями.

## 12. Воспроизводимость и исходники

Из корня `jev-agent`, с установленными зависимостями:

```bash
uv run --locked python -m scripts.measure_request_sizes
```

Для обновления приложенных примеров:

```bash
uv run --locked python -m scripts.measure_request_sizes --export-dir docs/request-examples
```

Скрипт не вызывает API. Для LLM используется настоящий `AsyncLLMExtractor`
с `httpx2.MockTransport`; для Jev — сборщик и сериализатор установленного SDK.
В генераторе зафиксированы учебные настройки, `.env` не загружается. Скрипт
проверяет валидность учебного предложения, обработку Python, совпадение двух
копий схемы и то, что при повторе меняется только feedback в контексте задачи.
Экспорт обновляет только перечисленные файлы примеров и `sizes.json`.
