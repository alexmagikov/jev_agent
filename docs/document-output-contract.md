# Требования к итоговому документу

Документ описывает результат обработки переписки: структурированный JSON-черновик
с актуальными значениями, источниками и результатами проверок. Он предназначен
для согласования требований, проверки примеров и подготовки разметки.
Это не описание юридически обязательных реквизитов банковского документа.
Подготовка черновика не означает выставления счёта или исполнения перевода.

Источником текущего поведения остаётся код. Правило классификации после исправлений
описано в [разделе 11](#11-классификация-после-исправлений).
Этот Markdown не подключается к промптам автоматически.

## 1. Какие документы поддерживаются

| `document_type`  | Условие выбора                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `invoice_draft`  | Есть актуальный запрос подготовить счёт на оплату товаров или услуг                                            |
| `transfer_draft` | Есть актуальный запрос перевести собственные деньги пользователя на его собственную карту |
| `none`           | Актуального запроса на поддерживаемый документ нет                                                                          |

Запросом может быть прямое поручение, выраженное намерение или короткая фраза
с типом документа и данными. Пользователь не обязан говорить «черновик».
Уточнение данных продолжает существующее поручение.

Счёт-фактура, УПД, акт и банковская выписка не являются `invoice_draft`.
Перевод другому человеку не является `transfer_draft`.
Вопрос об интерфейсе, просьба объяснить порядок действий или найти старый
документ сами по себе не являются поручением подготовить черновик.

Отсутствие суммы, ИНН, карты или банка не отменяет поддерживаемое поручение.
При отмене или явной просьбе отложить подготовку выбирается `none`, пока
пользователь не возобновит поручение. Простое упоминание другого документа
не заменяет действующий запрос.

Для `none` итог содержит `fields={}` и непустой текст `reason`.
Внутренние коды классификации `no_request`, `other_document`, `cancelled`
объясняют причину отказа, но поле `none_reason` в итоговый документ не входит.

## 2. Общая структура результата

| Ключ          | Требование                                                                                                                                                               |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `case_id`       | Непустая строка: идентификатор входного кейса                                                                                              |
| `document_type` | Одно из трёх значений из раздела 1                                                                                                                      |
| `fields`        | Все поля выбранного шаблона; для `none` — пустой объект                                                                                  |
| `confidence`    | Необязательное число от 0 до 1 либо `null`; уверенность классификации типа, а не всего заполнения       |
| `validation`    | Необязательный в схеме отчёт о проверках; обязателен при наличии помеченных непроверенных полей |
| `reason`        | Непустая строка только для `none`                                                                                                                         |

У счёта ровно 12 полей, у перевода — 5. Неизвестное поле включается в JSON
с соответствующим статусом и `value=null`. Пропуск ключа не заменяет `missing`.
Поля другого шаблона и произвольные дополнительные ключи не допускаются.

Каждое поле содержит:

| Ключ              | Смысл                                                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `status`            | Возможность заполнить поле по данным пользователя                             |
| `value`             | Значение нужного типа либо `null`                                                                |
| `evidence`          | Массив ID исходных сообщений пользователя                                              |
| `derivation`        | Запись о выполненном Python расчёте либо `null`                                            |
| `validation_status` | Только `"needs_review"` для проблемного поля; в обычном поле отсутствует |

`status` и `validation_status` отвечают на разные вопросы: первый описывает
предполагаемое состояние данных, второй — удалось ли подтвердить этот кандидат.

## 3. Статусы полей

Таблица относится к полям, прошедшим проверки. Исключения для сохранённого
непроверенного кандидата описаны в разделе 8.

| Статус  | Когда применяется                                                                                                                 | `value`                                                                                                                              | `evidence`                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `fillable`  | Значение прямо подтверждено пользователем или однозначно вычисляется                | Не `null`; заполненная строка не может быть пустой или состоять из пробелов | Нужны источники значения и исходных чисел                  |
| `missing`   | Актуальные применимые данные отсутствуют или не хватает данных для вычисления | `null`                                                                                                                               | Обычно `[]`; возможна ссылка на явный отзыв значения |
| `invalid`   | Пользователь указал применимые данные, но они имеют непригодный формат               | `null`                                                                                                                               | Сообщения с некорректными данными                                |
| `ambiguous` | В источнике остался неразрешённый выбор, смысл или принадлежность данных           | `null`                                                                                                                               | Сообщения с неоднозначностью                                         |

Примеры различий:

- ИНН не указан → `missing`.
- ИНН указан как 11 цифр → `invalid`, а не `missing`.
- Для одного реквизита предложены два подходящих варианта без выбора → `ambiguous`.
- Модель сомневается, хотя пользователь сообщил одно ясное значение → само
  сомнение модели не является основанием для `ambiguous`.
- Известна цена единицы, но неизвестно количество и нет общего итога → общая
  сумма `missing`, а не частичная сумма по известным позициям.

Неверно скопированное значение, выдуманная цитата и ошибочная формула — ошибки
извлечения. Их нельзя скрывать статусом `invalid`, если исходные данные пользователя
сами по себе пригодны.

## 4. Источники и актуальность

Источниками фактов служат сообщения с ролью `user`. Реплики ассистента могут
пояснять, к чему относится короткий ответ, но не подтверждают значение сами по себе.
Учитывается весь диалог, включая поздние исправления, выборы и отмены.

Позднее явное исправление заменяет раннее значение соответствующего поля.
Изменение одного реквизита не отменяет остальные. Исторические числа и чужие
реквизиты не используются как актуальные данные только потому, что они встретились
в переписке. Отзыв значения без замены оставляет поле `missing`.

Для счёта получатель — покупатель/заказчик, которому выставляется счёт.
Его реквизиты следует отличать от реквизитов продавца и других участников.
Для перевода сумма относится к самому переводу, а не к балансу, комиссии,
лимиту или прежней операции. Банк карты следует отличать от банка счёта списания.

Во внутреннем ответе извлекателя источники содержат `message_id` и дословный
`quote`. После JSON-декодирования цитата должна быть непустым фрагментом
соответствующего сообщения с неизменными кавычками, пробелами и пунктуацией.
В обычном итоговом `fields.*.evidence` сохраняются только ID, без повторов.
ID источников операндов расчёта также включаются в `evidence` результата.

Нормализация значения не разрешает переписывать цитату. Для одного значения
могут существовать разные достаточные наборы источников; равенство ID эталону
и смысловая достаточность доказательств — разные свойства.

## 5. Счёт на оплату: `invoice_draft`

### 5.1. Поля счёта

Тип в таблице указан для заполненного значения; при других статусах используется
`null`. Числа должны быть конечными JSON-числами, не строками и не `true`/`false`.

| Поле              | Тип                                       | Требование                                                                                                                                                                                                                                                                                                                   |
| --------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `recipient_name`    | Строка                                 | Название организации или ФИО покупателя/заказчика. ФИО приводится к именительному падежу только однозначно («счёт ИП Петрову» → «ИП Петров»); при неоднозначности сохраняется форма пользователя; компоненты имени не выдумываются, название организации сохраняется |
| `recipient_inn`     | Строка                                 | Целый исходный ИНН: ровно 10 или 12 ASCII-цифр; ведущие нули сохраняются                                                                                                                                                                                                             |
| `recipient_email`   | Строка                                 | Целый исходный адрес вида `local@domain.suffix`, без пробелов и дополнительных `@`                                                                                                                                                                                                 |
| `recipient_account` | Строка                                 | Целый расчётный счёт покупателя: ровно 20 ASCII-цифр                                                                                                                                                                                                                                              |
| `recipient_bik`     | Строка                                 | БИК банка покупателя: ровно 9 ASCII-цифр                                                                                                                                                                                                                                                                    |
| `subject`           | Строка                                 | Общее назначение счёта по правилам раздела 5.2                                                                                                                                                                                                                                                    |
| `items`             | Непустой массив позиций | Только актуальные выбранные товары/услуги; правила раздела 5.3                                                                                                                                                                                                                      |
| `amount_rub`        | Число больше 0                    | Общий итог счёта в рублях; правила раздела 5.4                                                                                                                                                                                                                                                      |
| `vat_mode`          | `"no_vat"` или `"rate"`               | Налоговый режим по словам пользователя                                                                                                                                                                                                                                                               |
| `vat_rate_percent`  | Число от 0 до 100                   | Только явно указанная ставка, включая 0; из сумм налога и базы не вычисляется                                                                                                                                                                                            |
| `basis_number`      | Строка                                 | Номер названного основания без `№` и внешних меток «договор/номер»; буквы, нули, дефисы и слеши сохраняются                                                                                                                                   |
| `basis_date`        | Строка                                 | Реальная календарная дата основания в формате `YYYY-MM-DD`; недостающие части не выдумываются                                                                                                                                                                  |

ИНН, счёт и БИК нельзя дополнять, обрезать или самостоятельно «исправлять».
Email копируется целиком: удалить первую букву адреса и получить другой
синтаксически допустимый адрес нельзя. Проверки формата не устанавливают
существование организации, счёта или адреса; реестры и контрольные суммы
для этих реквизитов не проверяются.

### 5.2. Назначение `subject`

Одна явно названная оплачиваемая категория может заполнять и `subject`, и `items`.
Отдельное предложение «назначение счёта» для этого не требуется.
Неизвестные количество или цена не отменяют названное назначение.

Для нескольких разных товаров нужно явно указанное общее назначение.
Нельзя самостоятельно склеивать их названия в `subject`.
`subject` записывается в именительном падеже с числом пользователя:
«за консультацию» → `консультация`, «за мониторы» → `мониторы`; названия в кавычках
не меняются.

| Поручение                                                                                 | `subject`                                                                 |
| -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| «Счёт за консультационные услуги»                                    | `консультационные услуги`                           |
| «Счёт за ручки и маркеры»                                                     | `missing`, если общего назначения больше нет |
| «Ручки и маркеры. Назначение: материалы для семинара» | `материалы для семинара`                              |
| «Счёт на 5000 рублей»                                                                | `missing`                                                                 |

### 5.3. Позиции `items`

Каждая позиция содержит ровно четыре атрибута:

| Атрибут     | Тип                                                    | Требование                                                                                                                         |
| ------------------ | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `description`    | Строка или `null`                              | Название выбранного товара/услуги; неизвестное название не выдумывается       |
| `quantity`       | Неотрицательное число или `null` | Количество этой позиции, прямо указанное или однозначно вычисленное               |
| `unit`           | Строка или `null`                              | Исходная единица измерения количества этой позиции                                              |
| `unit_price_rub` | Неотрицательное число или `null` | Цена одной единицы этой позиции, прямо указанная или однозначно вычисленная |

Выбранная позиция с одним известным описанием уже поддерживает
`items.status="fillable"`. Недостающие атрибуты остаются `null` и не переводят
весь список в `missing` или `ambiguous`. Отдельного `status` у атрибута позиции нет.
Из одной суммы, получателя или номера договора позиция не создаётся.

Обычное описание приводится к единственному числу именительного падежа,
если это однозначно: «стулья» → «стул». Смысл, характеристики, установленные
названия и слова только множественного числа («ножницы») сохраняются.
Общее слово-категория без указанного вида или количества сохраняется как написано:
«за услуги» → «услуги», «за работы» → «работы». С видом или количеством действует
обычное правило: «5 услуг настройки» → «услуга настройки».
Приведение описания к единственному числу не означает `quantity=1`.
`subject` по этому правилу не преобразуется.

У цитируемого названия можно убрать внешнее слово «товар/услуга» и внешние
кавычки. Текст внутри названия, внутренние кавычки и слова, входящие в само
название, сохраняются. Из `товар «Набор "Весна"»` получается `Набор "Весна"`.
Неподтверждённые цвет, материал, размер, модель и другие характеристики
не добавляются.

Единица копируется в исходной форме целиком, включая точку сокращения:
`шт.` сохраняется как `шт.`. В «4 часа по 2400 рублей за час» выбирается `часа`.
Единица из цены используется, если единица количества не названа.
Слово товара/услуги не превращается в единицу: «2 консультации» не даёт
`unit="консультации"`.

При «стол и либо стул, либо кресло — ещё решу» в список включается только стол.
Не выбранные альтернативы не считаются пропущенными позициями. Если ни одна
позиция не выбрана, список имеет `status="ambiguous"`, `value=null`.
При неопределённости атрибута выбранной позиции список остаётся `fillable`,
а соответствующий атрибут — `null`.

### 5.4. Итог, количество и цена

Явно указанный общий итог сохраняется даже при неизвестных количествах.
Одиночная сумма, относящаяся к поручению выставить счёт, считается итогом,
если контекст не указывает на цену единицы, частичную сумму или альтернативы.

При отсутствии явного итога вычисление допустимо, когда известна стоимость
каждой активной позиции: целая плата за работу/партию либо количество и цена
единицы. Частичный итог не подставляется вместо общей суммы.

| Условие                                                                                   | Результат                                                                                                                       |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| «Счёт за стулья на 5000 рублей», количество неизвестно | `amount_rub=5000`; количество и цена единицы не выводятся из итога                             |
| «Стулья по 5000 рублей», количество неизвестно               | Цена единицы известна, `amount_rub` — `missing`                                                                  |
| 100 рублей за каждую из двух работ                                      | Итог 200; `quantity=1` и цену единицы из этого не придумывают                                      |
| 100 рублей за обе работы вместе                                           | Итог 100                                                                                                                             |
| Два разных товара: всего 8 штук на 1600 рублей                   | Итог 1600; количество и цену каждой позиции нельзя распределить произвольно |
| Партия одного товара 5600 рублей, 8 штук                             | Цена единицы может вычисляться как 700, если разные цены не оговорены             |
| Неясно, относится число к единице или ко всей партии  | При неразрешённом контексте сумма `ambiguous`, `value=null`                                            |

Цены разных позиций не усредняются. Указанная скидка применяется только
к названной пользователем базе. Порядок скидки, налога и других действий
не выдумывается. Процент НДС сам по себе не разрешает увеличить итог.

### 5.5. НДС

| Данные пользователя           | `vat_mode`             | `vat_rate_percent`  |
| ----------------------------------------------- | ------------------------ | --------------------- |
| «Без НДС»                               | `fillable`, `no_vat` | `missing`, `null` |
| «НДС 0%»                                   | `fillable`, `rate`   | `fillable`, `0`   |
| «НДС 20%»                                  | `fillable`, `rate`   | `fillable`, `20`  |
| «С НДС» без ставки                  | `fillable`, `rate`   | `missing`, `null` |
| Налоговый режим не назван | `missing`, `null`    | `missing`, `null` |

`no_vat` и одновременно заполненная ставка недопустимы. При названной сумме
налога, но без явной ставки процент не вычисляется.

## 6. Перевод себе: `transfer_draft`

| Поле                    | Тип заполненного значения | Требование                                                                                                                                                                     |
| --------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `amount_rub`              | Число больше 0                        | Актуальная сумма перевода в рублях, прямо указанная или однозначно вычисленная                                       |
| `destination_card_masked` | Строка                                     | Ровно та полная маска карты, которую выбрал пользователь; символы маски, пробелы и цифры сохраняются |
| `destination_bank`        | Строка                                     | Банк выбранной карты получателя, в именительном падеже: «в Альфа-Банке» → «Альфа-Банк»; само название не меняется (`Сбер` остаётся `Сбер`) |
| `source_account_kind`     | Строка                                     | Явно названный тип счёта списания                                                                                                                           |
| `recipient_relation`      | Строка                                     | При явном переводе себе/на собственную карту — `self`                                                                                           |

Скрытые цифры карты не восстанавливаются. Маску нельзя сокращать до последних
четырёх цифр. Банк одной карты не переносится на другую без подтверждения.
Тип счёта не выводится только из делового контекста.

«Себе», «на свою карту», «на мою карту» могут подтверждать `self` без номера
карты и банка. Само решение классификатора выбрать `transfer_draft` не служит
доказательством `self`. В схеме это строка, а не отдельный перечислимый тип.

Разрешены эквивалентные написания одного подтверждённого значения:
`Сбер` / `Сбербанк`; `расчётный счёт` / `расчётный`. Банк записывается в именительном
падеже, поэтому `Сбера` вариантом не считается.
Этот список не выбирает банк или счёт вместо пользователя. Если выбран ВТБ,
значение `Сбербанк` остаётся ошибкой. Последующие исправления и отмены действуют
и для перечисленных вариантов.

## 7. Расчёты и итоговое представление

Извлекатель задаёт планы вычислений, Python выполняет арифметику, смысловая
проверка оценивает выбор исходных данных и соответствие операции поручению.
Числа подтверждаются сообщениями пользователя; внешние курсы, ставки и другие
отсутствующие исходные данные не добавляются.

Расчёт может заполнять общий `amount_rub`, а в счёте — `quantity` и
`unit_price_rub` конкретной позиции. Ставка НДС не вычисляется.
Неоднозначность или нехватка данных не оправдывают придуманную формулу.
Количество 1 из одного названия позиции не выводится.

Для прошедшего проверку расчёта `value` содержит результат, а `derivation` —
запись о вычислении. Формат этой строки предназначен для чтения человеком;
её не следует использовать как отдельную машинную схему формулы.
Результат вычисления не обязан встречаться в переписке дословно.
Python округляет вычисленные `amount_rub` и `unit_price_rub` до копеек по правилу
half-up (0,005 → 0,01); в `derivation` тогда добавляется `rounded_to_kopecks=…`.
Вычисленное количество не округляется: неточный результат отклоняется.

В обычных итоговых полях нет `calculation`, `quantity_calculation`,
`unit_price_calculation`, `operands` или полных цитат. Они относятся к внутреннему
предложению извлекателя. Для непроверенных кандидатов эти данные могут отдельно
сохраняться в `validation.unverified_fields`.

## 8. Результаты проверок и `needs_review`

`validation` имеет следующий состав:

| Ключ              | Значения и смысл                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `status`            | `passed` или `needs_review` — общий результат проверок                                            |
| `python_status`     | `passed` или `needs_review`                                                                                              |
| `semantic_status`   | `passed`, `needs_review` или `not_run`                                                                                 |
| `issues`            | Массив замечаний с `path`, `stage`, `code`, `message`                                                   |
| `unverified_fields` | Исходные кандидаты проблемных полей, включая цитаты и планы расчётов |

`stage` замечания — `python`, `semantic` или `llm_response`.
Путь может обозначать поле, атрибут позиции или конкретную часть источника.
У документа с `status="passed"` список замечаний пуст. Наличие замечаний
требует `validation.status="needs_review"`.

В `full` прошедший все проверки черновик получает `python_status="passed"`
и `semantic_status="passed"`. В `llm-only` смысловая проверка не выполняется:
`semantic_status="not_run"`; успешная Python-проверка может давать общий `passed`.
Следовательно, общий `passed` не означает обязательное участие Jev и не
гарантирует полноту документа для выпуска.

Решение `none` также получает общий `passed`, но `semantic_status="not_run"`:
проверка полей для него не запускается. В метриках принятия оно учитывается как
результат обработки кейса. Правильность содержимого оценивается отдельно от
проверок: правильный кандидат с `needs_review` сохраняет балл за содержимое,
но не считается автоматически принятым. Подробнее — раздел «Оценка качества» README.

Когда попытки исправления исчерпаны, обычный пайплайн может сохранить лучший
из кандидатов с `needs_review`: прошедший Python-проверку, затем с меньшим числом
непроверенных полей, при равенстве — более поздний. Проблемные поля получают
`validation_status="needs_review"`, а замечание указывает на соответствующий путь.
Независимые поля сохраняются и проверяются отдельно.

У такого поля значение может быть неподтверждённым; если его нельзя представить
или вычислить, оно может остаться `null` даже при `status="fillable"`.
Это исключение разрешено только вместе с отметкой `needs_review` и отчётом
о проблеме. Такой кандидат нельзя использовать как проверенное заполнение.
Невычисленный результат нельзя заменять нулём или вымышленным числом.

При ошибке Python смысловая проверка этого кандидата не запускается.
Если не получен ни один структурно пригодный кандидат или произошёл сбой API,
кейс может завершиться отдельной ошибкой обработки. Это не `document_type="none"`.
В строгом парном аудите используется `allow_partial=False`: непроверенный
кандидат не превращается в принятую пару результатов.

## 10. Критерии правильного результата

Результат следует оценивать по нескольким независимым признакам:

1. Правильно выбран тип актуального поручения.
2. Присутствует точный набор полей выбранного шаблона.
3. Статусы отражают исходные данные, а не уверенность модели.
4. Значения относятся к нужной сущности, позиции и числовой роли.
5. Учтены последние применимые исправления и отмены.
6. Источники существуют, принадлежат пользователю и обосновывают значение
   или исходные данные расчёта.
7. Не добавлены отсутствующие атрибуты, реквизиты и характеристики.
8. Вычисления используют подходящие исходные числа, действие и область применения.
9. Непроверенные поля явно отделены через `validation` и `validation_status`.

Корректная JSON-схема сама по себе не подтверждает смысл значений.
С другой стороны, отсутствие реквизита не делает черновик ошибочным, если
в переписке этого реквизита действительно нет и указан статус `missing`.

## 11. Классификация после исправлений

Исправления сохраняют тип документа, только пока актуальное
поручение соответствует условиям поддерживаемой операции.

| Диалог                                                                        | Ожидаемый результат по ограничению операции |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| «Переведи себе 5000». «Нет, на другую мою карту» | `transfer_draft`                                                                 |
| «Переведи себе 5000». «Нет, переведи маме»           | `none`, причина неподдерживаемой операции         |
| «Переведи маме». «Нет, переведи себе» | `transfer_draft` |
| «Выставь счёт покупателю А». «Покупателя исправь на Б» | `invoice_draft` |

Классификатор получает весь входной диалог до извлечения полей. Сначала он учитывает
последние применимые исправления, затем проверяет ограничения поддерживаемой операции.
При переходе «маме → себе» выбирается черновик перевода на собственную карту;
отсутствующие реквизиты остаются полями со статусом `missing`.

Этот порядок задан в `src/cases/document_type.py` для обоих независимых вопросов
Jev: типа документа и причины `none`. Правила выбора типа и критерии причины
также используются LLM-классификацией в режиме `llm-only`.
Дополнительного запроса классификации нет. При последующем ремонте полей
выбранный тип документа не изменяется.

Смысловые правила находятся в промптах и не все обеспечиваются одной Pydantic-схемой.
Например, схема принимает строку единицы, а правило выбора `часа` вместо `час`
требует учесть контекст количества. Поэтому примеры и требования проверяются
как по структуре, так и по сообщениям пользователя.
